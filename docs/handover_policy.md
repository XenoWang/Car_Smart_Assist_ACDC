# 接管边界判定策略

> 本文档定义「什么时候应该把控制权交还给司机」的标签口径。
> 这是本项目最核心、也最需要说清楚的设计，因为它**不是 ACDC 数据集自带的标注**，
> 而是本项目自己构造的监督信号。

> 2026-09-25：运行时规则已实现，见第 6 节；第 3 节仍是待验证的标签构造方案，
> 不等于当前代码已经训练了接管分类器。当前输出为接管请求，不执行车辆控制权切换。

---

## 1. 为什么这件事必须自己定义

ACDC 提供语义分割与图像对应关系，不提供任何与「驾驶决策」相关的标注。
所以「接管边界」这个任务没有现成标签可用，必须由项目自己构造。

这一步的选择直接决定了整个项目是不是成立，因此单独立文档。

---

## 2. 边界条件的定义

把接管边界设计成**三档有序分级**，而不是二分类。

| 等级 | 名称 | 含义 | 对应提示强度 |
|------|------|------|--------------|
| 0 | `clear` | 当前条件下辅助驾驶可继续运行 | 不提示 |
| 1 | `approaching` | 接近能力边界，需要司机提高注意力 | 轻提示 |
| 2 | `takeover_required` | 已越过边界，应立即交还控制权 | 强提示 / 建议立即接管 |

**为什么不用二分类**：
二分类只能回答「现在要不要接管」，无法表达「还有多远到边界」。
而实际驾驶中最有价值的信息恰恰是预警 —— 在到达边界之前给出缓冲时间。
三档分级让模型可以输出「接近边界」，这是安全价值最高的那一档。

## 3. 标签构造方法

### 3.1 构造依据

标签由以下可量化的因子合成，每个因子都有明确的数据来源：

| 因子 | 来源 | 说明 |
|------|------|------|
| 天气/光照条件 | ACDC 子集标签（fog/night/rain/snow） | 唯一的高质量原生标签 |
| 路面可见度 | 分割结果（可行驶区域占比、边界清晰度） | 由 Stage 1 分割头提供 |
| 最近前车距离 | 距离头 / 外部距离标注 | 相对风险的直接度量 |
| 最近来车距离 | 距离头 / 外部距离标注 | 会车场景的相对速度是叠加的 |
| 场景复杂度 | 分割类别多样性、检测目标数 | 复杂度越高，边界越近 |

### 3.2 合成规则

```
risk_score = base_weather_risk(weather)
           × (1 + complexity_factor)
           × distance_risk(nearest_lead_distance) × lead_direction_factor
           × distance_risk(nearest_oncoming_distance) × oncoming_factor
```

标签构造方案的候选阈值（尚未实现，不是运行时 policy 配置）：

- `risk_score < T1` → 等级 0
- `T1 ≤ risk_score < T2` → 等级 1
- `risk_score ≥ T2` → 等级 2

阈值取值初始设为 `T1 = 0.35`、`T2 = 0.70`，后续用验证集上的
precision-recall 曲线标定，标定过程写进 `artifacts/reports/`。

### 3.3 非对称代价

**漏报的代价远高于误报。**

- 漏报：该接管没提醒 → 司机在超出系统能力的场景下继续依赖辅助驾驶 → 安全事故
- 误报：不该提醒却提醒了 → 司机被打扰 → 体验下降，长期会导致司机忽略提示

因此：
- 等级 2 的召回率是**第一优先指标**，优先级高于准确率和 F1
- 损失函数对等级 2 的漏报施加更高权重（见 `perception/losses/classification.py`）
- 评测必须单独报告漏报率，见 `evaluation/metrics/classification.py`

## 4. 已知的方法论问题（必须正视）

### 4.1 规则蒸馏的循环性

标签由规则生成，模型再去拟合规则 —— 这本质上是**知识蒸馏**，
模型不会超过规则，也无法发现规则没考虑到的危险情形。

如果不处理，这个任务在技术审查时会被直接质疑。

**处理办法**（按优先级）：

1. **人工标注一个小子集**：从 ACDC 中分层抽样约 300-500 帧，
   人工按第 2 节的等级定义标注，作为「规则标签」的校验集。
   报告里给出规则标签与人工标注的一致率（Cohen's kappa），
   如实呈现规则在哪些场景与人类判断不符。**这一项是必须做的。**
2. **利用 ACDC 的 correspondences**：同一场景在不同时刻/视角的对应关系
   可以提供时间维度的一致性约束，减少单帧标签的抖动。
3. **把规则本身当作 baseline**：报告里同时给出「纯规则」和「学习模型」的指标，
   说明学习模型相对规则是否有增益。如果没有增益，就该如实写出来
   并分析原因（这比硬凑一个提升更专业）。

### 4.2 与真实接管数据无关

本项目的「接管边界」是基于感知可观测量的构造性定义，
**不是真实人类驾驶员的接管行为统计**。
真实接管数据（如某些车队数据集）会有驾驶员个体差异、疲劳、注意力分散等因素，
本项目不涉及。

这个局限必须在 README 和报告中明确写出，不能含糊成「判断何时应该接管」。

### 4.3 无法覆盖的场景

单目视觉 + 语义分割无法感知的边界条件，本项目一律**不声称覆盖**：

- 车辆自身机械故障、爆胎
- 传感器被遮挡（镜头泥污、强光直射）
- 非视觉信号：施工指示、交警手势、临时交通管制
- 极端情况下的道路塌陷、异物

这些必须在文档中显式列为「超出感知能力范围」，
而不是等别人指出。主动划清边界比事后被问出来强得多。

## 6. 已实现的运行时规则（2026-09-25）

### 6.1 风险与接管分别输出

`risk.assess_risk` 消费图像对应的 `PerceptionResult`，输出 `RiskAssessment`：
风险等级、识别证据、缺失信息、触发规则、主风险目标索引和 `reliable`。
风险等级包括 `none / notice / warning / critical / unknown`。
`none` 只表示未触发当前规则；`unknown` 表示不足以判断。
若部分目标有效而另一些信息缺失，保留最高已知风险，同时 `reliable=false`。

`handover_rules.evaluate_handover` 在以下任一条件成立时输出 `request_takeover`：

1. 无法可靠判断：能见度不可用、必要字段缺失、低置信度、目标方向未知、距离无效等。
2. 已识别证据达到 `critical`。
3. 接管分类头给出可信的 2 级结果。

可信的 0 级不能覆盖其他接管条件。分类头默认可以缺省，`require_handover_head=true` 可设为必需。
该模块只请求司机接管，驾驶员确认与车辆控制接口没有实现。

### 6.2 基于已识别情况的风险计算

原始置信度乘能见度乘子后必须达到 `min_confidence_for_clear`（默认 0.7）。
默认 DEGRADED 乘子 0.6，因此现有组合下 DEGRADED 感知结果不足以解除接管请求。
天气类别置信度不足仅记为诊断信息，不单独请求接管，也不施加恶劣天气倍率；
若目标检测等其他必需感知结果缺失，接管原因来自这些缺失结果。
能见度门控判为 `BLIND`（清晰度极差）时，跳过后续感知并直接请求驾驶员接管；
`DEGRADED` 表示清晰度下降但继续感知，降级后的必要结果若低于置信度门槛，仍会请求接管。

对每个有效目标计算：

```text
保守距离 = max(0, distance_m - uncertainty_sigma * distance_uncertainty_m)
规则距离 = 保守距离 / weather_risk_multiplier / direction_factor
规则距离 < 15 → critical；< 30 → warning；< 50 → notice；否则 none
```

这里的数值均来自集中配置，等于阈值时落入下一档。
只有已确认对向目标使用对向倍率；方向未知只采信距离，同时请求接管。
提供了无效或相对过大的距离标准差时，不继续采信该目标的距离。
默认允许省略标准差，使用原始距离；可通过 `require_distance_uncertainty=true` 强制要求。
天气识别本身可触发配置的风险提示等级，能见度下降可触发 notice；最终取全部有效证据的最高等级。
天气分类或天气类别不确定本身不直接请求接管；清晰度极差时由 `VisibilityGate` 的 `BLIND` 结果触发。

目标检测成功后必须明确设置 `object_detection_available=true`。
`true + []` 表示该帧检测未检出目标，`false + []` 表示无可用检测结果。
新增的 clear 天气配置仅供未来可识别正常天气的预测器使用，不把 ACDC 四类天气自动映射成 clear。

### 6.3 输出与限制

生成器把规则结果写入 `AdvisoryResult.policy_details`，理由写入 `evidence`，模板只负责表达。
配置异常或没有感知结果时返回未知风险并请求接管。
原有门控 BLIND→critical 映射保留，`source=visibility_gate` 表示该等级来自能见度导致的紧急接管要求；
它不能解读为已检测到具体障碍物。`source=policy` 的等级依据本节识别证据规则。

本规则没有自车速度、相对速度、车道冲突或碰撞时间输入；近距离与对向倍率仅作为初始提示规则。
它不能区分相邻车道正常会车与真实碰撞轨迹，也不能保证发现检测器漏检的目标。
当前 Stage 1 模型仍是骨架，测试验证规则逻辑和管线契约，真实场景误报/漏报及阈值效果需另行标定。

2026-09-26 增加独立的四类天气小模型：读取 ACDC 子集标签训练并输出可解释视觉线索。
雨后反光、疑似湿润区域、亮白积雪代理和低对比度均是单帧视觉估计，
不等于水深、道路实际积雪面积或雾中米制可视距离；目前不直接据此提高接管等级。
类别判断足够可信时才进入本节的天气风险规则，缺少目标检测时仍请求接管。
天气分类低置信度只留下诊断信息，不直接触发接管。天气类别用于提供风险线索；
清晰度极差时由能见度门控请求接管，不把雾、雨、雪类别本身当成清晰度或严重程度的测量值。
