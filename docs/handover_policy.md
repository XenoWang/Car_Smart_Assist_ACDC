# 接管边界判定策略

> 本文档定义「什么时候应该把控制权交还给司机」的标签口径。
> 这是本项目最核心、也最需要说清楚的设计，因为它**不是 ACDC 数据集自带的标注**，
> 而是本项目自己构造的监督信号。

---

## 1. 为什么这件事必须自己定义

ACDC 提供语义分割与图像对应关系，不提供任何与「驾驶决策」相关的标注。
所以「接管边界」这个任务没有现成标签可用，必须由项目自己构造。

这一步的选择直接决定了整个项目是不是成立，因此单独立文档。

---

## 2. 边界条件的定义

把接管边界设计成**三档有序分级**，而不是二分类。

| 等级 | 名称 | 含义 | 对应提示强度 |
|------|------|------|--------------|
| 0 | `clear` | 当前条件下辅助驾驶可继续运行 | 不提示 |
| 1 | `approaching` | 接近能力边界，需要司机提高注意力 | 轻提示 |
| 2 | `takeover_required` | 已越过边界，应立即交还控制权 | 强提示 / 建议立即接管 |

**为什么不用二分类**：
二分类只能回答「现在要不要接管」，无法表达「还有多远到边界」。
而实际驾驶中最有价值的信息恰恰是预警 —— 在到达边界之前给出缓冲时间。
三档分级让模型可以输出「接近边界」，这是安全价值最高的那一档。

## 3. 标签构造方法

### 3.1 构造依据

标签由以下可量化的因子合成，每个因子都有明确的数据来源：

| 因子 | 来源 | 说明 |
|------|------|------|
| 天气/光照条件 | ACDC 子集标签（fog/night/rain/snow） | 唯一的高质量原生标签 |
| 路面可见度 | 分割结果（可行驶区域占比、边界清晰度） | 由 Stage 1 分割头提供 |
| 最近前车距离 | 距离头 / 外部距离标注 | 相对风险的直接度量 |
| 最近来车距离 | 距离头 / 外部距离标注 | 会车场景的相对速度是叠加的 |
| 场景复杂度 | 分割类别多样性、检测目标数 | 复杂度越高，边界越近 |

### 3.2 合成规则

```
risk_score = base_weather_risk(weather)
           × (1 + complexity_factor)
           × distance_risk(nearest_lead_distance) × lead_direction_factor
           × distance_risk(nearest_oncoming_distance) × oncoming_factor
```

阈值口径（与 `configs/model/advisory_llm.yaml` 的 `policy` 段保持一致）：

- `risk_score < T1` → 等级 0
- `T1 ≤ risk_score < T2` → 等级 1
- `risk_score ≥ T2` → 等级 2

阈值取值初始设为 `T1 = 0.35`、`T2 = 0.70`，后续用验证集上的
precision-recall 曲线标定，标定过程写进 `artifacts/reports/`。

### 3.3 非对称代价

**漏报的代价远高于误报。**

- 漏报：该接管没提醒 → 司机在超出系统能力的场景下继续依赖辅助驾驶 → 安全事故
- 误报：不该提醒却提醒了 → 司机被打扰 → 体验下降，长期会导致司机忽略提示

因此：
- 等级 2 的召回率是**第一优先指标**，优先级高于准确率和 F1
- 损失函数对等级 2 的漏报施加更高权重（见 `perception/losses/classification.py`）
- 评测必须单独报告漏报率，见 `evaluation/metrics/classification.py`

## 4. 已知的方法论问题（必须正视）

### 4.1 规则蒸馏的循环性

标签由规则生成，模型再去拟合规则 —— 这本质上是**知识蒸馏**，
模型不会超过规则，也无法发现规则没考虑到的危险情形。

如果不处理，这个任务在技术审查时会被直接质疑。

**处理办法**（按优先级）：

1. **人工标注一个小子集**：从 ACDC 中分层抽样约 300-500 帧，
   人工按第 2 节的等级定义标注，作为「规则标签」的校验集。
   报告里给出规则标签与人工标注的一致率（Cohen's kappa），
   如实呈现规则在哪些场景与人类判断不符。**这一项是必须做的。**
2. **利用 ACDC 的 correspondences**：同一场景在不同时刻/视角的对应关系
   可以提供时间维度的一致性约束，减少单帧标签的抖动。
3. **把规则本身当作 baseline**：报告里同时给出「纯规则」和「学习模型」的指标，
   说明学习模型相对规则是否有增益。如果没有增益，就该如实写出来
   并分析原因（这比硬凑一个提升更专业）。

### 4.2 与真实接管数据无关

本项目的「接管边界」是基于感知可观测量的构造性定义，
**不是真实人类驾驶员的接管行为统计**。
真实接管数据（如某些车队数据集）会有驾驶员个体差异、疲劳、注意力分散等因素，
本项目不涉及。

这个局限必须在 README 和报告中明确写出，不能含糊成「判断何时应该接管」。

### 4.3 无法覆盖的场景

单目视觉 + 语义分割无法感知的边界条件，本项目一律**不声称覆盖**：

- 车辆自身机械故障、爆胎
- 传感器被遮挡（镜头泥污、强光直射）
- 非视觉信号：施工指示、交警手势、临时交通管制
- 极端情况下的道路塌陷、异物

这些必须在文档中显式列为「超出感知能力范围」，
而不是等别人指出。主动划清边界比事后被问出来强得多。

## 5. 阈值配置位置

所有阈值只在以下位置定义，**不允许在代码里硬编码**：

- `configs/model/advisory_llm.yaml` → `advisory.policy.*`
- 标签构造阶段用 `configs/data/distance_supplement.yaml` → `valid_range_m` 等

阈值调整需要记录在 `docs/adr/` 中，说明调整原因与指标影响。
