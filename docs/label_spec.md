# 标签规范

> 本文档是标签口径的**唯一权威来源**。代码、配置、评测脚本中任何与本文档不一致的地方，
> 都以本文档为准，并且需要修复代码。
>
> 修改本文档属于**破坏性变更**：已有 checkpoint 与评测报告全部失效，必须重新训练。

---

## 1. 语义分割标签

| 项目 | 定义 |
|------|------|
| 类别体系 | Cityscapes 19 类 |
| ignore_index | 255 |
| 映射函数 | `data/label_mapping.py` |
| 调色板 | 官方 Cityscapes 调色板，保证可视化跨实验可比 |

**为什么用 Cityscapes 19 类而不是 ACDC 原始类**：
Cityscapes 上的预训练权重可以直接复用，且 19 类是分割领域的通用基准，
便于和公开结果对比。

## 2. 路况分类标签

| 项目 | 定义 |
|------|------|
| 类别 | fog / night / rain / snow |
| 编码 | 0 / 1 / 2 / 3（对应 `configs/data/acdc.yaml` 的子集顺序） |
| 标签类型 | 单标签（softmax） |
| 来源 | ACDC 官方子集划分 |

**已知简化**：真实场景可能同时下雪且有雾，但 ACDC 的子集是互斥的。
这是数据集本身的限制。若后续需要多标签，改为 BCE 并同步更新
`perception/heads/road_condition.py` 与 `configs/model/perception_multitask.yaml`。

## 3. 接管边界标签

| 项目 | 定义 |
|------|------|
| 类别 | 0=clear / 1=approaching / 2=takeover_required |
| 编码 | 有序整数（**有序**，不是 one-hot 无序类别） |
| 类型 | 三档有序分级 |
| 来源 | **本项目构造**，口径见 `docs/handover_policy.md` |

**有序性的影响**：等级之间不是等距的，但顺序有意义。
如果后续尝试序回归（ordinal regression），这个标签可以直接用；
如果当作无序多分类处理，需要注意这会丢失顺序信息。

## 4. 检测标签

| 项目 | 定义 |
|------|------|
| ACDC 原始格式 | **COCO JSON**，`bbox` 为 `[x, y, w, h]`（左上角坐标 + 宽高） |
| 内部统一格式 | `[x1, y1, x2, y2]`，绝对像素坐标，左上原点 |
| 坐标系 | 变换后的图像坐标（**不是原图坐标**） |
| ACDC 类别 | 8 类，用 Cityscapes ID（见 4.4） |
| 方向（前车/来车） | **独立属性，不在上述 8 类里**，需另行推导（见 4.1） |
| 最小框高 | 20 px（小于此值丢弃） |
| 最大截断比例 | 0.3（超过此值丢弃） |

> ⚠️ 两个格式陷阱，写测试时必须覆盖：
> 1. **COCO 的 `bbox` 是 `[x, y, w, h]` 不是 `[x1, y1, x2, y2]`** —— 直接当 xyxy 用会
>    把宽高当右下角坐标，得到一个完全错误但不会报错的框。
> 2. **ACDC 的检测框对应的是 1920×1080 原图**，若模型输入做了 resize，
>    框必须跟着变换（与分割掩码用同一套几何变换）。

**来车与前车的区分依据**：两者的安全含义不同 ——
前车过近的处理是减速，来车过近的处理是注意会车，不能让模型混淆。

### 4.1 方向标签（「前车 / 来车」）—— 用序列时序推导

> ⚠️ **已确认（基于实际解压数据）**：ACDC 的检测标注**不包含任何朝向或 3D 信息**。
> 标注字段全集仅七个：`area, bbox, category_id, id, image_id, iscrowd, segmentation`。
> 没有 `location`、没有 `rotation_y`、没有深度。
>
> 因此「用 3D 朝向角推导方向」这条路**在 ACDC 上不可行**。
> `configs/model/perception_multitask.yaml` 早期配置的 `strategy: yaw_angle`
> 是照搬 KITTI 的能力，ACDC 没有对应的数据支撑 —— 该配置已更正。

**采用方案：从 ACDC 的视频序列时序推导方向标签。**

ACDC 的图像按视频序列组织，文件名形如
`{sequence}_frame_{frame:0>6}_rgb_anon.png`，同一 sequence 内帧号连续。
目标在画面中的运动方式是可直接观测的：

```
在同一 sequence 内对目标做跨帧关联（跟踪）
    ├── 横向位置持续向画面一侧移动，且尺寸先增大后消失  → 对向（来车）
    ├── 横向位置基本稳定，方位角缓慢变化                → 同向（前车）
    └── 无法判定（出现帧数太少 / 被遮挡 / 跟踪断裂）     → unknown
```

**关键设计：时序只用于离线生成标签，推理仍然是单帧。**
好处是既拿到了 ACDC 域内的真方向标签（无域差异），又不破坏现有的单帧推理架构 ——
不需要在模型里引入 RNN/时序模块，不需要维护帧间状态。

**标签编码：**
```
同向 (leading)  :  0
对向 (oncoming) :  1
unknown         : -1    ← 不参与方向分类损失，但仍参与检测框回归
```

**判定阈值必须标定，不要拍脑袋。** 实现时从每个天气子集抽一小批序列，
人工核对跟踪结果，用这批数据确定「横向位移多少才算对向」等阈值，
标定过程与最终阈值一并补写入本节。

**unknown 的处理**：不参与方向分类损失，但仍参与检测框回归。
宁可不对方向表态，也不要给错 —— 方向错会导致完全相反的驾驶建议
（前车近该减速，来车近该注意会车）。

**KITTI 侧的参考**：KITTI 的 `rotation_y`（第 15 字段）可直接给出朝向角，
可用于交叉验证时序推导的可靠性。但 KITTI 在本项目中只负责距离监督，
不参与方向标签的生成 —— 避免方向也背上域差异。

### 4.2 KITTI 的 `DontCare` 必须特殊处理

KITTI 标注里有一类 **`DontCare`**，实测占目标总数的 **26%**（抽查 800 帧：1514/5782）。
它标记的是「标注员认为这里可能有目标但未标注」的区域。

**这不是背景，不能当负样本用。** 如果训练时把 `DontCare` 区域当背景，
模型会学到「车辆附近的位置是背景」这种自相矛盾的信号，直接压低召回率。

处理方式：
- 训练时从负样本中排除 `DontCare` 区域（或在检测损失里 mask 掉这些位置）
- 评测时同时报告「把 DontCare 当背景」和「排除 DontCare」两套指标，
  说明这个选择对指标的影响 —— 这个细节在面试里能体现对数据集的真实掌握

**其他 KITTI 类别映射：**

| KITTI 类别 | 本项目处理 |
|------------|------------|
| Car / Van | 保留，合并为「车辆」 |
| Pedestrian / Cyclist | 保留为独立类别（虽不直接服务于距离任务，但对场景复杂度判断有用） |
| Misc | 丢弃 |
| DontCare | **排除出负样本**，见上 |

### 4.3 ACDC 与 KITTI 的分辨率不一致

实测：KITTI 目标检测图像为 **1224×370**（约 3.3:1），ACDC 为 **1920×1080**（16:9）。

这会影响两件事：
1. **统一分辨率的选择** —— `configs/data/acdc.yaml` 里写的 `train_size: [1024, 512]`（2:1）
   对两者都不是原生比例，需要重新决定
2. **相机内参** —— 缩放会改变内参，两个数据集必须各自维护自己缩放后的内参矩阵

**不要**用一套硬编码的内参跑两个数据集。`perception/geometry/pinhole.py`
的内参更新函数必须对两者都正确，`tests/unit/test_geometry.py` 要覆盖这一点。

### 4.4 ACDC 检测标注：实际格式与一处官方缺陷

以下全部基于实际解压后的文件核实，不是转述。

**类别清单**（COCO `categories`，ID 沿用 Cityscapes 体系）：

| ID | 名称 | supercategory | train 集实例数 |
|----|------|---------------|---------------|
| 26 | car | vehicle | 6657 |
| 24 | person | human | 1692 |
| 27 | truck | vehicle | 537 |
| 33 | bicycle | vehicle | 392 |
| 32 | motorcycle | vehicle | 250 |
| 25 | rider | human | 227 |
| 31 | train | vehicle | 212 |
| 28 | bus | vehicle | 168 |

> `train` 是**铁路列车**（Cityscapes 沿用的类别）。城市道路场景中出现 212 个实例
> 值得怀疑是标注噪声或确实途经铁路。**不要**把它当作"训练集"的笔误，
> 处理时按异常类对待，实现阶段核对一下原始图像再决定是否并入。

**标注条目字段**：`iscrowd, category_id, bbox, area, segmentation, image_id, id`
`segmentation` 是 **COCO RLE 压缩格式**，解码需要 `pycocotools`（已列入依赖）。

**划分文件**（每个文件含 `images` / `categories` / `annotations` 三个键）：

| 文件 | 图像数 | 标注数 |
|------|--------|--------|
| `gt_detection/instancesonly_train_gt_detection.json` | 1600 | 10135 |
| `gt_detection/instancesonly_val_gt_detection.json` | 406 | 2794 |
| `gt_detection/{fog,night,snow}/instancesonly_*_{train,val}_gt_detection.json` | 各 400/100+ | 见下 |
| `gt_detection/*/instancesonly_*_test_image_info.json` | 2000 总量 | **无标注**（test 标注按基准惯例不公开） |

各天气 train：fog 400 图/2290 标注、night 400/2975、snow 400/2831。
各天气 val：fog 100/640、night 106/559、rain 100/763、snow 100/832。

> 🐞 **官方打包缺陷（已用 md5 确证）**
>
> `gt_detection/rain/instancesonly_rain_train_gt_detection.json` 与
> `gt_detection/instancesonly_train_gt_detection.json` **md5 完全相同**
> （`176582bc2b69a8e05dbcc88123ec041e`），都是 1600 图 / 10135 标注。
> 即 per-condition 的 **rain/train 文件是错的**，内容是全部天气的合并结果。
>
> **影响**：按天气分层采样或做 rain 子集消融时，若读这个文件会静默拿到全量数据。
> **规避**：需要 rain 的训练子集时，从 all-conditions 文件按 `file_name` 前缀
> （`rain/train/`）过滤，**不要读那个 per-condition 文件**。
> `rain/val` 是正常的（100 图 / 763 标注），可直接用。

## 5. 距离标签（口径最容易出错，逐条写清）

### 5.1 参考系

```
    ┌─────────────────┐
    │   相机（前挡风）  │
    └─────────────────┘
           │  ← camera_to_ego 偏移 [0, 0, 1.5] m（校准后填入真实值）
    ┌──────┴──────────┐
    │      自车         │
    └──┬───────────┬──┘
       ↑ 后轴中心（原点）
```

| 项目 | 定义 |
|------|------|
| 起点 | **自车后轴中心**（不是相机光心） |
| 终点 | 目标检测框的**底边中心**（不是框中心） |
| 单位 | 米 |
| 有效范围 | `[2.0, 80.0]` m |

**为什么终点取底边中心**：底边中心在地面上的投影最接近目标车辆与地面接触的位置，
这是车辆实际占据的空间位置。取框中心会因为目标高度不同引入系统性偏差。

**为什么起点取后轴中心而不是相机**：驾驶决策关心的是车身与目标的距离，
不是镜头与目标的距离。两者差一个约 1.5 m 的安装偏移 —— 这个偏移很小，
所以混用时不会立刻发现，但会引入稳定偏差，在最关键的近距区间（<15m）占比可观。

> ⚠️ **混用两个口径是本项目最容易犯且最难发现的错误**。
> `tests/unit/test_geometry.py` 中必须有专门验证这一点的测试。

### 5.2 距离分桶

评测必须分桶报告，不允许只给一个总体 MAE：

| 桶 | 范围 |
|----|------|
| near | 2 – 15 m |
| medium | 15 – 40 m |
| far | 40 – 80 m |

**理由**：单目测距的误差随距离增长很快。总体 MAE 会被大量近处样本拉低，
产生「测距很准」的错觉，而远处实际上已经完全不可用。
分桶报告能如实呈现这一点，也便于说明「本系统在多远范围内可用」。

### 5.3 无效标签的处理

| 情形 | 处理 |
|------|------|
| 无距离标注的帧 | `valid=False`，损失中 mask |
| 距离超出 `[2, 80]` m | `valid=False`，丢弃（**不截断到边界**） |
| 框被截断 > 30% | `valid=False`（底边中心不可靠） |
| 框高 < 20 px | `valid=False`（测距误差过大） |
| 目标被遮挡 | 若遮挡比例可估计则按比例判定，否则标 `valid=False` |

> ⚠️ **绝对不要用 0 填充无效距离。** 0 会被当作「距离 0 米」参与训练，
> 教模型把「看不清」和「贴脸」混为一谈。这是一个会产生安全隐患的错误。

### 5.4 不确定度

距离头额外输出不确定度估计。这是给 Stage 2 用的：
模型对某帧没把握时，提示策略应当更保守。

不确定度**不参与** Stage 1 的指标报告（它没有真值），
只在 Stage 2 的决策中使用，并在报告中以校准曲线（预测不确定度 vs 实际误差）的形式呈现。

## 6. 指令数据标签（Stage 2）

| 项目 | 定义 |
|------|------|
| 格式 | chat jsonl，`{"image": ..., "conversations": [{role, content}, ...]}` |
| loss 计算 | **只对 assistant 回复计算**，system 与 user 部分 mask 掉 |
| 划分 | 按 ACDC scene 切分，与 Stage 1 使用**同一套** split.json |
| 负样本比例 | 不低于 40%（必须包含大量「可以不接管」的情形） |

**负样本比例为什么重要**：
如果训练数据里绝大多数样本都是「建议接管」，
模型会学成一个永远喊接管的复读机 —— 在指标上可能表现很好（漏报率极低），
但实际完全不可用（误报率接近 100%）。

因此评测必须同时看漏报率和误报率（见 `configs/train/advisory_sft.yaml`）。
